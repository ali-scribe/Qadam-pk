# Requirements Document

## Introduction

Qadam transforms confusing Pakistani institutional documents — scholarship circulars, government service requirements, university admission notices — into personalized, evidence-backed action plans. The user uploads a document image; the system extracts structured information from it, asks only the profile questions that are relevant to that specific document's criteria, and produces an ordered action plan with an eligibility verdict.

The product is meaningfully different from a general AI summarizer because:
- Output is personalized to the user's specific answers, not generic
- Every important claim is traceable to a specific excerpt from the source document
- Information not present in the document is explicitly marked as unknown — never fabricated
- The user receives an actionable, ordered plan, not just a summary

The MVP is scoped to a single-developer, beginner/intermediate-level build using only free-tier services. No authentication, no database, no custom ML.

## Pre-Specification Analysis

### Ambiguities Resolved Before Writing Requirements

| Ambiguity | Resolution |
|---|---|
| What makes a question "relevant"? | Relevant = directly derived from an extracted eligibility criterion in Stage 1 output. The AI generates questions as a field in the Stage 1 JSON; no separate call. |
| What claims require evidence? | All eligibility criteria, required documents, deadlines, fees, and application steps must have a non-null `evidence` field. |
| Distinction between "unknown" and "not applicable" | `null` = field exists in the document schema but the document does not state a value. Fields that don't apply to the document type are omitted from output. |
| What is "ordered" in the action plan? | Ordered by logical dependency and urgency (deadlines first, prerequisites before dependent steps). The AI is responsible for this ordering. |
| File size limit (not previously defined) | 10 MB client-side limit, enforced before any API call. |
| Evidence text definition | A verbatim excerpt from the source document, or a close paraphrase clearly identified as paraphrase. Not a generated summary. |
| "Likely eligible" disclaimer | The UI must render a disclaimer alongside any eligibility verdict that Qadam is not a legal advisor and the user should verify with the issuing authority. |

### Conflicting Requirements Resolved

| Conflict | Resolution |
|---|---|
| "Gracefully handle unreadable documents" vs "always return structured JSON" | Stage 1 JSON includes a `readable` boolean field. When `false`, all extraction fields are null/empty and the pipeline halts after Stage 1 with a clear message. |
| "No chatbot" vs "ask questions" | Questions are a structured form generated from Stage 1 output, rendered as a static form. There is no conversational loop. |

### Scope Cuts (Not in MVP)

- Multi-page document handling
- Drag-and-drop upload (standard `<input type="file">` only)
- Urdu-language output
- PDF or DOCX file support
- User accounts, history, or saved plans

### Technical Risks Documented

1. **Gemini 10s timeout** — Vercel Hobby serverless functions time out at 10 seconds. Mitigation: compress images client-side to ≤1 MB before sending. If this is insufficient, reduce prompt verbosity before seeking a timeout increase.
2. **Gemini schema non-compliance** — Gemini may return JSON that does not match the declared schema despite using `responseSchema`. Mitigation: validate the full shape server-side before forwarding to the client.
3. **Evidence hallucination** — Gemini may produce plausible but fabricated evidence excerpts. Mitigation: the prompt instructs verbatim copy from visible document text. This is a known LLM limitation; it is documented here and handled by the testing checklist, not eliminated by code alone.

## Glossary

- **Pipeline**: The end-to-end sequence of Upload → Stage 1 Analysis → Questions → Stage 2 Plan.
- **Stage 1**: The first AI call. Takes a document image, returns a `DocumentAnalysis` JSON object.
- **Stage 2**: The second AI call. Takes the `DocumentAnalysis` object and the user's answers, returns an `ActionPlan` JSON object.
- **DocumentAnalysis**: The TypeScript type defining the structured output of Stage 1.
- **ActionPlan**: The TypeScript type defining the structured output of Stage 2.
- **UploadStep**: The UI stage where the user selects and submits a document image.
- **SummaryStep**: The UI stage that displays the extracted document information after Stage 1.
- **QuestionsStep**: The UI stage where the user answers profile questions generated by Stage 1.
- **PlanStep**: The UI stage that displays the eligibility verdict and action plan after Stage 2.
- **EligibilityVerdict**: One of three values: `likely_eligible`, `likely_not_eligible`, `cannot_determine`.
- **EvidenceText**: A verbatim excerpt from the source document, or a close paraphrase explicitly identified as such.
- **UnknownMarker**: A `null` value assigned to a field that is part of the document's schema but whose value is not stated in the uploaded document.
- **Gemini_Client**: The server-side module that wraps all calls to the Google Gemini API.
- **API_Route_Analyze**: The Next.js API route at `/api/analyze` that handles Stage 1.
- **API_Route_Plan**: The Next.js API route at `/api/plan` that handles Stage 2.
- **Pipeline_Context**: The React Context that holds the current pipeline stage, DocumentAnalysis, user answers, and ActionPlan across all UI components.
- **Storage_Util**: The localStorage utility that persists DocumentAnalysis and ActionPlan across page refreshes.

### Requirement 1: Document Image Upload

**User Story:** As a Pakistani citizen or student, I want to upload a photo or screenshot of a document, so that Qadam can read and analyze it without me having to type anything.

#### Acceptance Criteria

1. THE UploadStep SHALL render a file input (`<input type="file">`) that accepts image file types: `image/jpeg`, `image/png`, `image/webp`, and `image/gif`.
2. WHEN a user selects a file that is not one of the accepted image types, THE UploadStep SHALL display an inline error message stating the accepted formats, SHALL clear the file selection, and SHALL NOT proceed to Stage 1.
3. WHEN a user selects a file whose size exceeds 10 MB, THE UploadStep SHALL display an inline error message stating the 10 MB limit and SHALL NOT proceed to Stage 1.
4. WHEN a user attempts to submit the upload form without selecting a file, THE UploadStep SHALL display a validation message and SHALL NOT proceed to Stage 1.
5. WHEN a valid image file is selected and submitted, IF the file size is already ≤ 1 MB, THE UploadStep SHALL encode it as-is; IF the file size exceeds 1 MB, THE UploadStep SHALL compress it to ≤ 1 MB before encoding.
6. WHEN a valid image file is selected and submitted, THE UploadStep SHALL encode the (compressed if necessary) image as a base64 string and pass it to API_Route_Analyze.
7. WHILE Stage 1 is in progress, THE UploadStep SHALL display a loading indicator and SHALL disable the submit button to prevent duplicate submissions.
8. THE UploadStep SHALL be usable on a 375px wide viewport, meaning all interactive elements SHALL be reachable without horizontal scrolling, all buttons and inputs SHALL have a minimum touch-target height of 44px, and all body text SHALL be at minimum `text-sm` (14px).
9. THE UploadStep SHALL NOT use drag-and-drop as the only upload mechanism — the standard file input must always be present and functional.
10. WHEN API_Route_Analyze returns a non-2xx response or the network request fails, THE UploadStep SHALL display an error message and SHALL re-enable the file input and submit button so the user can retry without refreshing the page.

### Requirement 2: Stage 1 — Document Analysis

**User Story:** As a user, I want the system to extract all structured information from my document automatically, so that I do not have to read and interpret the document myself.

#### Acceptance Criteria

1. WHEN API_Route_Analyze receives a valid base64-encoded image, THE Gemini_Client SHALL send the image to the Gemini API with a prompt that instructs extraction of: `documentType`, `purpose`, `eligibilityCriteria`, `requiredDocuments`, `deadlines`, `fees`, `applicationSteps`, `warnings`, `unknownFields`, and `questionsForUser`.
2. THE Gemini_Client SHALL request a response with `responseMimeType: "application/json"` and SHALL include an explicit JSON schema in the prompt for all extracted fields.
3. WHEN the Gemini API returns a response, THE API_Route_Analyze SHALL validate that the response is valid JSON, that all required top-level fields are present, and that all array fields (`eligibilityCriteria`, `requiredDocuments`, `deadlines`, `fees`, `applicationSteps`, `warnings`, `unknownFields`, `questionsForUser`) are of type array before returning the response to the client.
4. IF any required top-level field of `DocumentAnalysis` is absent, of the wrong type, or IF any array field is not an array in the Gemini response, THEN THE API_Route_Analyze SHALL return HTTP 500 with `{ "error": "AI returned an unrecognized response structure. Please try again." }`.
5. WHEN a field in the document schema has no corresponding value in the uploaded document, THE Gemini_Client prompt SHALL instruct Gemini to set that field to `null` — not to guess, infer, or fabricate a value.
6. THE `DocumentAnalysis` type SHALL include a `readable` boolean field. WHEN the document is too blurry, dark, or low-resolution to extract meaningful information, THE Gemini_Client prompt SHALL instruct Gemini to set `readable` to `false` and set all extraction fields to `null` or empty arrays.
7. THE `DocumentAnalysis` type SHALL include a `documentScope` field that indicates whether the document is within Qadam's scope (a Pakistani institutional document). WHEN the uploaded image is not a recognizable institutional document, THE Gemini_Client prompt SHALL instruct Gemini to set `documentScope` to `"out_of_scope"`.
8. WHEN API_Route_Analyze returns a valid `DocumentAnalysis` object, THE Pipeline_Context SHALL store it and advance the pipeline to the SummaryStep.
9. THE Storage_Util SHALL persist the `DocumentAnalysis` object to localStorage so that it survives a page refresh.
10. IF the Gemini API returns a non-2xx HTTP status, THEN THE API_Route_Analyze SHALL return HTTP 502 with an error message that describes the problem and suggests a user action — the message SHALL NOT include the API key, stack trace, or raw API error body.
11. IF the Gemini API call does not complete within 9 seconds, THEN THE API_Route_Analyze SHALL return HTTP 504 with `{ "error": "The analysis took too long. Please try again with a clearer image." }`.
12. IF the Gemini API response is not valid JSON, THEN THE API_Route_Analyze SHALL catch the parse error and return HTTP 500 with `{ "error": "The AI returned an unexpected response. Please try again." }`.
13. WHEN API_Route_Analyze receives a `DocumentAnalysis` where `readable` is `false`, THE route SHALL return HTTP 200 with the `DocumentAnalysis` object and THE Pipeline_Context SHALL advance to the SummaryStep, which is responsible for halting further pipeline progression.
14. WHEN API_Route_Analyze receives a `DocumentAnalysis` where `documentScope` is `"out_of_scope"`, THE route SHALL return HTTP 200 with the `DocumentAnalysis` object and THE Pipeline_Context SHALL advance to the SummaryStep, which is responsible for halting further pipeline progression.

### Requirement 3: Document Summary Display

**User Story:** As a user, I want to see what the system extracted from my document before answering questions, so that I can verify the extraction is correct and understand what document was recognized.

#### Acceptance Criteria

1. WHEN the Pipeline_Context advances to SummaryStep, THE SummaryStep SHALL display the `documentType` and `purpose` fields from `DocumentAnalysis`. IF either field is `null`, THE SummaryStep SHALL display "Not stated in document" for that field.
2. IF `DocumentAnalysis.readable` is `false`, THEN THE SummaryStep SHALL display a message stating the document could not be read and advising the user to try a clearer or better-lit photo, SHALL render a "Try a different image" button that returns the user to the UploadStep, and SHALL NOT display any other extraction fields or the "Continue to questions" button.
3. IF `DocumentAnalysis.readable` is `true` AND `DocumentAnalysis.documentScope` is `"out_of_scope"`, THEN THE SummaryStep SHALL display a message stating the document was not recognized as a supported type and SHALL render a "Try a different document" button that returns the user to the UploadStep.
4. IF `DocumentAnalysis.readable` is `true` AND `DocumentAnalysis.documentScope` is not `"out_of_scope"`, THEN THE SummaryStep SHALL display all extracted fields: eligibility criteria, required documents, deadlines, fees, application steps, and warnings. For each field whose value is `null`, THE SummaryStep SHALL display "Not stated in document". For each array field that is an empty array (`[]`), THE SummaryStep SHALL display a label such as "None found in document".
5. WHEN a displayed field value has a non-null, non-empty `evidence` property, THE SummaryStep SHALL render a "View source" button adjacent to that value. WHEN the "View source" button is activated, THE SummaryStep SHALL display the EvidenceText inline using the visual treatment defined in Requirement 7, Criterion 5.
6. IF a field's `evidence` property is `null` or an empty string, THEN THE SummaryStep SHALL NOT render any evidence interaction for that field.
7. IF `DocumentAnalysis.readable` is `true` AND `documentScope` is not `"out_of_scope"`, THEN THE SummaryStep SHALL render a "Continue to questions" button that advances the pipeline to the QuestionsStep.
8. THE SummaryStep SHALL be usable on a 375px wide viewport without horizontal scrolling and with all interactive elements having a minimum touch-target height of 44px.
9. THE SummaryStep SHALL render all body text at a minimum of Tailwind's `text-sm` (14px).

### Requirement 4: Dynamic Profile Questions

**User Story:** As a user, I want to be asked only the questions that are relevant to my document's specific criteria, so that I do not waste time answering irrelevant questions.

#### Acceptance Criteria

1. THE QuestionsStep SHALL render only the questions present in `DocumentAnalysis.questionsForUser` — it SHALL NOT render a static, pre-defined question list.
2. WHEN `DocumentAnalysis.questionsForUser` is an empty array, THE QuestionsStep SHALL display a message stating that no profile questions are needed for this document and SHALL render a "Generate action plan" button to proceed directly to Stage 2.
3. THE QuestionsStep SHALL render a labeled form field for each question in `questionsForUser`. Questions marked as `required: true` in the `DocumentAnalysis` SHALL render with an asterisk (*) adjacent to the field label as the required indicator.
4. WHEN a user attempts to submit the questions form with one or more `required: true` questions left unanswered, THE QuestionsStep SHALL display an inline validation message that names each unanswered required field and SHALL NOT proceed to Stage 2.
5. WHEN all required questions are answered and the form is submitted, THE QuestionsStep SHALL pass the `DocumentAnalysis` object and the user's answers to API_Route_Plan.
6. WHILE Stage 2 is in progress, THE QuestionsStep SHALL display a loading indicator and SHALL disable the submit button.
7. IF API_Route_Plan returns an error response or the network request fails, THEN THE QuestionsStep SHALL display an error message indicating the plan could not be generated and SHALL re-enable the submit button so the user can retry without refreshing the page.
8. THE QuestionsStep SHALL be usable on a 375px wide viewport, meaning all form fields, labels, the required indicator, validation messages, and the submit button SHALL be fully visible without horizontal scrolling and all interactive elements SHALL have a minimum touch-target height of 44px.
9. THE QuestionsStep SHALL render all form labels and body text at a minimum of Tailwind's `text-sm` (14px).

### Requirement 5: Stage 2 — Eligibility Reasoning and Action Plan

**User Story:** As a user, I want the system to reason about my eligibility and give me a concrete action plan based on my specific situation, so that I know exactly what to do next.

#### Acceptance Criteria

1. WHEN API_Route_Plan receives a valid `DocumentAnalysis` object and a non-null user answers map containing at least one key-value entry, THE Gemini_Client SHALL send both to the Gemini API with a prompt that instructs it to: assess eligibility, categorize each criterion as satisfied/unmet/unknown, and produce an ordered list of action items.
2. THE Gemini_Client SHALL request the Stage 2 response with `responseMimeType: "application/json"` and SHALL include an explicit JSON schema for the `ActionPlan` type.
3. THE `ActionPlan` type SHALL include: `eligibilityVerdict` (one of `"likely_eligible"`, `"likely_not_eligible"`, `"cannot_determine"`), `verdictRationale` (string), `satisfiedCriteria` (array of `{ text: string; evidence: string | null }`), `unmetCriteria` (array of `{ text: string; reason: string; evidence: string | null }`), `unknownCriteria` (array of `{ text: string; evidence: string | null }`), and `actionItems` (array of `{ title: string; description: string; evidence: string | null; deadline: string | null }`).
4. WHEN the Gemini API returns a response, THE API_Route_Plan SHALL validate that all required top-level fields are present, that all array fields are of type array, and that each element within `satisfiedCriteria`, `unmetCriteria`, `unknownCriteria`, and `actionItems` contains the required fields specified in Criterion 3, before returning the response to the client.
5. IF any required top-level field of `ActionPlan` is absent, of the wrong type, or IF any array field is not an array, or IF any array element is missing a required field, THEN THE API_Route_Plan SHALL return HTTP 500 with `{ "error": "AI returned an unrecognized response structure. Please try again." }`.
6. THE API_Route_Plan route SHALL return `actionItems` in the order provided by Gemini without client-side reordering. The Stage 2 prompt SHALL instruct Gemini to order items by logical dependency and urgency — deadline-driven items first, prerequisites before dependent steps.
7. WHEN API_Route_Plan validates the `ActionPlan`, THE route SHALL verify that no criterion whose corresponding answer was null or absent in the user answers map appears in `satisfiedCriteria`. IF such a criterion is found in `satisfiedCriteria`, THE route SHALL return HTTP 500 with `{ "error": "AI returned an unrecognized response structure. Please try again." }`.
8. IF the Gemini API returns a non-2xx HTTP status, THEN THE API_Route_Plan SHALL return HTTP 502 with an error message that describes the problem and suggests a user action.
9. IF the Gemini API call does not complete within 9 seconds, THEN THE API_Route_Plan SHALL return HTTP 504 with `{ "error": "The plan took too long to generate. Please try again." }`.
10. IF the Gemini API response is not valid JSON, THEN THE API_Route_Plan SHALL catch the parse error and return HTTP 500 with `{ "error": "The AI returned an unexpected response. Please try again." }`.
11. WHEN API_Route_Plan returns a valid `ActionPlan`, THE Pipeline_Context SHALL store it and advance the pipeline to the PlanStep.
12. WHEN THE Pipeline_Context stores a valid `ActionPlan`, THE Storage_Util SHALL write it to localStorage such that reloading the page restores the object with all fields intact.
13. IF `ActionPlan.actionItems` is an empty array, THE PlanStep SHALL display an explicit message such as "No specific action items could be determined from this document" — it SHALL NOT render an empty list.

### Requirement 6: Action Plan Display

**User Story:** As a user, I want to see my eligibility verdict and a clear ordered list of next steps with supporting evidence, so that I know exactly what I need to do and why.

#### Acceptance Criteria

1. WHEN the Pipeline_Context advances to PlanStep, THE PlanStep SHALL display the `eligibilityVerdict` such that each of the three verdict values (`likely_eligible`, `likely_not_eligible`, `cannot_determine`) produces a unique visible label and a visually non-identical color or icon indicator — a tester must be able to distinguish the three states without reading the label text alone.
2. THE PlanStep SHALL display the `verdictRationale` beneath the verdict. IF `verdictRationale` is `null` or an empty string, THE PlanStep SHALL display "Rationale not provided" in its place.
3. THE PlanStep SHALL display a disclaimer stating that Qadam is not a legal advisor and the user should verify eligibility with the issuing authority. On a 375px viewport, this disclaimer SHALL be visible in the initial viewport without scrolling.
4. THE PlanStep SHALL display `satisfiedCriteria`, `unmetCriteria`, and `unknownCriteria` each under a separate heading. IF any of these arrays is empty, THE PlanStep SHALL display a label such as "None" under that heading rather than omitting the section.
5. WHEN `ActionPlan.actionItems` is a non-empty array, THE PlanStep SHALL render each action item in the order returned by the API, numbered sequentially starting from 1.
6. IF `ActionPlan.actionItems` is an empty array, THEN THE PlanStep SHALL display an explicit message such as "No specific action items could be determined from this document" — it SHALL NOT render an empty numbered list.
7. WHEN `ActionPlan.actionItems` is rendered and an action item has a non-null, non-empty `evidence` property, THE PlanStep SHALL render a "View source" button adjacent to that action item.
8. WHEN a "View source" button is activated, THE PlanStep SHALL display the EvidenceText inline using the visual treatment defined in Requirement 7, Criterion 5. WHEN the button is activated again, THE PlanStep SHALL collapse the EvidenceText.
9. IF an action item's `evidence` property is `null` or an empty string, THEN THE PlanStep SHALL NOT render a "View source" button for that item.
10. WHEN an action item has a `deadline` field that is a non-null, non-empty string, THE PlanStep SHALL display it adjacent to the action item description.
11. THE PlanStep SHALL render a "Start over" button that clears Pipeline_Context and Storage_Util state and returns the user to the UploadStep.
12. THE PlanStep SHALL be usable on a 375px wide viewport without horizontal scrolling, with all interactive elements having a minimum touch-target height of 44px.
13. THE PlanStep SHALL render all body text at a minimum of Tailwind's `text-sm` (14px).

### Requirement 7: Evidence Integrity

**User Story:** As a user, I want to trust that the sources shown to me are real, so that I can verify claims against the original document myself.

#### Acceptance Criteria

1. THE Gemini_Client Stage 1 prompt SHALL explicitly instruct Gemini to populate every `evidence` field with a verbatim excerpt from the visible document text — not with a generated summary or inference.
2. THE Gemini_Client Stage 1 prompt SHALL explicitly instruct Gemini to set an `evidence` field to `null` if the corresponding value cannot be directly traced to text visible in the document image.
3. WHEN a `DocumentAnalysis` object is received by API_Route_Analyze, THE route SHALL verify that every item in `eligibilityCriteria`, `requiredDocuments`, `deadlines`, and `fees` arrays has an `evidence` key present. IF the `evidence` key is absent from any item, THE route SHALL treat it as `null` before forwarding the response to the client.
4. IF the evidence normalization in Criterion 3 fails due to a non-array field, THE API_Route_Analyze SHALL return HTTP 500 with `{ "error": "AI returned an unrecognized response structure. Please try again." }`.
5. WHEN a "View source" button is activated anywhere in the UI, THE UI SHALL display the EvidenceText in a visually distinct block styled as a blockquote — with a left border, indented padding, and a font style (italic or muted color) that differentiates it from Qadam-generated text — and SHALL NOT render a "View source" button for any item whose `evidence` value is `null` or an empty string.

### Requirement 8: No Invented Information

**User Story:** As a user in a high-stakes application context, I want the system to tell me when it doesn't know something rather than guess, so that I do not act on fabricated information.

#### Acceptance Criteria

1. THE Gemini_Client Stage 1 prompt SHALL contain an explicit instruction that reads, in substance: "If a field's value is not stated in the document, set it to null. Do not guess, infer, or fabricate values."
2. WHEN `DocumentAnalysis` contains a `null` deadline field, THE SummaryStep SHALL render "Deadline: Not stated in document" — it SHALL NOT render a blank, a dash, or a guessed date.
3. WHEN `DocumentAnalysis` contains a `null` fee field, THE SummaryStep SHALL render "Fees: Not stated in document".
4. WHEN `DocumentAnalysis` contains a `null` eligibility criterion value, THE SummaryStep SHALL render the criterion with "Value: Not stated in document".
5. THE `DocumentAnalysis` type SHALL include an `unknownFields` array that lists the names of fields Gemini could not determine from the document. IF `unknownFields` is a non-empty array, THE SummaryStep SHALL display it under the heading "Could not determine from document".
6. WHEN a criterion's satisfiability cannot be determined from the user's answers, THE API_Route_Plan prompt SHALL classify it as `"unknown"` in `unknownCriteria` — not as `"unmet"`.
7. WHEN `DocumentAnalysis` contains a `null` `applicationSteps` field or an empty `applicationSteps` array, THE SummaryStep SHALL render "Application steps: Not stated in document" or "None found in document" respectively — it SHALL NOT render a blank section.
8. WHEN `DocumentAnalysis` contains a `null` `warnings` field or an empty `warnings` array, THE SummaryStep SHALL render "Warnings: Not stated in document" or "None found in document" respectively.

### Requirement 9: Error States and Recoverability

**User Story:** As a user, I want clear error messages and a way to retry when something goes wrong, so that a failed attempt does not strand me on a broken screen.

#### Acceptance Criteria

1. WHEN API_Route_Analyze returns any non-2xx response, THE UploadStep SHALL display an error message. IF the response body contains an `error` field, THE UploadStep SHALL display that string. IF the `error` field is absent, THE UploadStep SHALL display a fallback message: "Something went wrong. Please try again." THE UploadStep SHALL render a "Try again" button that re-enables the upload form without requiring a page refresh.
2. WHEN API_Route_Plan returns any non-2xx response, THE QuestionsStep SHALL display an error message using the same fallback logic as Criterion 1 and SHALL render a "Try again" button that re-enables the questions form without requiring a page refresh.
3. IF a network error occurs during any API call (fetch throws, no response received), THEN THE UI SHALL display the message "Could not reach the server. Check your connection and try again." and SHALL render a recovery button appropriate to the current step.
4. WHEN an error state is active in the UploadStep or QuestionsStep, THE user SHALL be able to return to the previous step via a "Go back" button without refreshing the page.
5. THE Pipeline_Context SHALL never advance to the next step while an error state is active.
6. API_Route_Analyze and API_Route_Plan SHALL never include a raw stack trace, API key fragment, or internal error object in any response body — all responses SHALL use the `{ "error": string }` shape.

### Requirement 10: Session Persistence

**User Story:** As a user, I want my progress to be saved so that if I accidentally refresh the page, I do not lose the analysis or action plan.

#### Acceptance Criteria

1. WHEN a valid `DocumentAnalysis` object is received, THE Storage_Util SHALL write it to localStorage under the key `"qadam_document_analysis"`.
2. WHEN a valid `ActionPlan` object is received, THE Storage_Util SHALL write it to localStorage under the key `"qadam_action_plan"`.
3. WHEN the application loads, THE Pipeline_Context SHALL read localStorage and restore the pipeline as follows: IF both keys are present and valid, restore to the PlanStep; IF only `"qadam_document_analysis"` is present and valid, restore to the QuestionsStep; IF neither key is present or valid, start at the UploadStep.
4. IF reading from localStorage throws (e.g., storage is full or corrupted), THE Pipeline_Context SHALL catch the error, clear both localStorage keys, and start at the UploadStep.
5. THE Storage_Util SHALL NOT persist the uploaded image binary or any raw user answer values — only the structured AI outputs.
6. WHEN the user activates the "Start over" function, THE Storage_Util SHALL clear both localStorage keys and THE Pipeline_Context SHALL reset to the UploadStep.

### Requirement 11: TypeScript Type Safety

**User Story:** As the developer, I want strict TypeScript types for all AI output shapes, so that shape mismatches are caught at compile time rather than at runtime in production.

#### Acceptance Criteria

1. THE `lib/types.ts` file SHALL define and export the `DocumentAnalysis` type and the `ActionPlan` type as explicit TypeScript interfaces or types — not as `any` or `object`.
2. THE `DocumentAnalysis` type SHALL NOT use `any` for any field — fields of uncertain shape SHALL use `unknown` with type guards or a union type.
3. THE `ActionPlan` type SHALL NOT use `any` for any field.
4. THE `tsconfig.json` SHALL have `"strict": true` enabled.
5. WHEN `next build` is run, THE build SHALL complete with zero TypeScript errors.
6. WHEN `next build` is run, THE build SHALL complete with zero ESLint errors.
7. THE production build (`NODE_ENV=production`) SHALL contain no `console.log` calls in any compiled output file — debug logging SHALL be removed or gated behind a `process.env.NODE_ENV === 'development'` check.

### Requirement 12: Mobile Responsiveness

**User Story:** As a Pakistani user likely on a mobile device, I want the full pipeline to be usable on my phone, so that I am not excluded by my hardware.

#### Acceptance Criteria

1. IF the viewport width is 375px, THE UploadStep SHALL render with no content clipped and no horizontal scroll bar.
2. IF the viewport width is 375px, THE SummaryStep SHALL render with no content clipped and no horizontal scroll bar.
3. IF the viewport width is 375px, THE QuestionsStep SHALL render with all form fields reachable and submittable, with no horizontal scroll bar.
4. IF the viewport width is 375px, THE PlanStep SHALL render with all evidence interactions having a minimum tap-target size of 44×44 CSS pixels, with no horizontal scroll bar.
5. THE entire application SHALL NOT use text smaller than Tailwind's `text-sm` (14px) for any body content or form label.
6. THE file input in the UploadStep SHALL be a standard HTML `<input type="file">` element that triggers the native file picker on mobile browsers — no drag-and-drop-only mechanism is permitted.

### Requirement 13: Production Deployment

**User Story:** As the developer, I want a clean, deployable build on Vercel's free tier, so that the product can be demonstrated publicly.

#### Acceptance Criteria

1. THE application SHALL be deployable to Vercel on the Hobby (free) tier using zero-config Next.js deployment.
2. THE `GEMINI_API_KEY` environment variable SHALL be the only secret required for deployment — it SHALL be set in Vercel project settings and SHALL NOT appear in any committed file.
3. WHEN deployed, THE application's API routes SHALL be able to reach the Gemini API and return a `DocumentAnalysis` or `ActionPlan` object that conforms to the TypeScript types defined in `lib/types.ts`, within the Vercel Hobby 10-second function timeout.
4. THE deployed application SHALL serve the full pipeline end-to-end over HTTPS.
5. WHEN `next build` is run locally before deployment, THE build SHALL succeed with zero TypeScript errors and zero ESLint errors.
